# Jev workers в режиме jev/auto

На macOS с CanvasTTY доступны штатные видимые Jev-воркеры. На Linux/Windows
переносимый MCP допускает только задачи без записи, пока файловое ownership
для `codex exec` не будет отдельно проверено. Отказ на задачу с записью не
обходи другим способом.

Ограничение на способ создания сабагентов действует только при активной модели
`jev/auto`. При ручном выборе модели штатное делегирование Codex доступно;
используй этот навык только если выбран именно Jev-воркер. Browser Use,
Computer Use и компакт контекста остаются под Jev в обоих режимах.

Делегируй только независимую задачу с проверяемым результатом. Для каждого
воркера назначь отдельные файлы или рабочую папку; не запускай конкурирующие
правки одних файлов. Короткий вопрос и следующий зависимый шаг делай сам.
Для простого анализа публичного либо разрешённого текста без инструментов,
если OmniRoute настроен, используй его напрямую по
`OMNIROUTE-AGENT-INSTRUCTIONS.md`;
отдельный Codex-воркер увеличит общий расход. Воркер `jev/auto`, когда он
действительно нужен, уже получает модели через настроенный маршрут; не запускай внутри
него второй модельный вызов только ради выбора провайдера.

## Запуск

Для исследования без записи передай read_only: true, пустой
allowed_files и новую пустую cwd; harness проверит, что папка
осталась пустой.
Для Browser Use укажи `capabilities: ["browser"]`: такой воркер запускается
в штатном терминале CanvasTTY и использует MCP `jev-browser.browser_task`.
Брокер держит полный DOM внутри процесса, спрашивает Jev перед действиями и
возвращает короткий проверенный результат. `clicked: true` без перехода не
считай успехом; адресный fallback допускается только для явно указанного href.
Сырые `canvastty_browser` инструменты оставь для диагностики.
Плагин браузера Codex через `node_repl` в CanvasTTY не подключён.
После динамического поиска браузерных инструментов запросы идут на Luna 6:
текущий OmniRoute не принимает `tool_search_output` в истории внешней модели.

1. Вызови только `mcp__jev_workers__execute` (ожидание до 50 секунд) или
   `mcp__jev_workers__submit` (долгая задача). Передай уникальный `request_id`,
   конкретную `goal`, абсолютную `cwd`, относительные `allowed_files`,
   необходимые `acceptance_commands` как массивы аргументов и краткие
   `mandatory_instructions`. Если задача требует UI или файловых форматов,
   добавь только нужные `capabilities`: `browser`, `computer`, `pdf`,
   `documents`. Передавай лишь контекст, нужный воркеру.
   Если MCP инструмент отложен, один раз найди его через `tool_search` с
   `query: "jev-workers execute"` либо `"jev-workers submit"`. При ошибке
   обнаружения остановись; не угадывай shell команды и не запускай `npx`.
2. Если ответ остаётся активным, вызывай `mcp__jev_workers__collect` с
   `task_id` и `wait_seconds` до 50. Не трать ходы модели на частый опрос.
   `status` используй для диагностики, `cancel` — только своего задания.
3. Сверь результат с файлами и проверками независимо. Статус сервиса или
   текст воркера сами по себе не доказывают завершение задачи.

Не используй `collaboration.spawn_agent`, вложенный `codex exec`, старые
`gemini_submit`/`gemini_execute` и ручные `requested_model` либо ID аккаунта.
Если MCP или лестница недоступны, сообщи о сбое и выполни работу в текущем
агенте; не создавай воркера другим способом. Воркер не создаёт детей.

Каждый воркер работает в одном собственном диалоге `jev/auto`. Jev выбирает
модель и глубину рассуждения; сервер подставляет ID аккаунтов и модели из
защищённого локального конфига. ID аккаунтов, конкретные модели и состояние квот не
хранятся в этом навыке. Смена провайдера не требует нового воркера и не
сбрасывает его историю. Проверка действий инструментов и сжатие контекста
остаются в глобальных хуках Codex.
